# Migrating from v1 to v2

The canonical v2 entry points are an eagerly executed function carrying the flow
decorator and a ProcessingTemplate. Results come back as a `RunReport`; `status`,
the per-tile results, warnings and errors are all read from that one schema. This
guide does not ask you to throw your handler classes away in one step: it combines
a mechanical conversion with a small amount of manual work.

## 1. Inspect the existing code

Take the following v1-style file as `legacy.py`.

<!-- test: legacy-source -->
```python
import rdetoolkit.workflows as legacy_workflows


class TextHandler:
    def process(self, srcpaths, resource_paths):
        source = next(srcpaths.inputdata.glob("*.txt"))
        destination = resource_paths.struct / "structured.txt"
        destination.write_text(source.read_text(encoding="utf-8"), encoding="utf-8")


def custom_dataset_function(srcpaths, resource_paths):
    TextHandler().process(srcpaths, resource_paths)


if __name__ == "__main__":
    legacy_workflows.run(custom_dataset_function=custom_dataset_function)
```

`migrate check` is a read-only command that reports migration points.
`migrate apply` is a dry run by default and prints the converted flow function.
Only after reviewing it, pass `--no-dry-run -o <another directory>`. The input
file is never rewritten in place.

<!-- test: migration-commands -->
```bash
$ python -m rdetoolkit migrate check legacy.py
$ python -m rdetoolkit migrate apply legacy.py
```

Constructs that cannot be converted, such as dynamic dispatch, are left behind as
`TODO(rdetoolkit-migrate)`. Even without a TODO, check the generated code's tests
and output directory before adopting it.

## 2. The intermediate form: wiring handlers with `as_node`

An existing handler that satisfies an Appendix M Protocol can, for the migration
period only, have a method turned into an ordinary node with `as_node`. The
Protocol helps with this migration decision; it is not a DI mechanism and not an
entry point for new designs.

<!-- test: as-node-bridge -->
```python
from rdetoolkit import as_node


class LegacyReader:
    def read(self, name: str) -> str:
        return name.upper()


read_legacy = as_node(LegacyReader(), method="read", id="docs.migration.legacy_reader")
result = read_legacy("sample.txt")
assert result == "SAMPLE.TXT"
```

The class may stay at this stage, but pass values between nodes as explicit
arguments and do not add hidden state such as `self.df`.

## 3. Choose the final form

If a domain template exists, check its slots with `skeletons show <name>` and
implement only the TODO slots of the class generated by
`new processing <name>`. The template owns the skeleton, the save
order and the output conventions.

For irregular processing without a template, write one function with the flow
decorator. `if`, loops, f-strings, literal arguments and default arguments behave
exactly as in ordinary Python. Split work into functions with the node decorator
only when you want to reuse it. Use the builtin nodes in `rdetoolkit.nodes` for
saving.

For measured metadata, use the public `build_meta(values, metadef_path)` node,
then `save_meta(metadata, out)`. The definition controls filtering, type
conversion, key order, units (including `$Key` references), and variable rows.
Use `repeated={key: values}` for repeated columns; scalar values for variable
definitions become one row. `Metadata.units` holds constant units and
`Metadata.variable` holds rows of value/unit cells. `parse_invoice_meta` applies
the same rules to the invoice's nested `custom` section. User flows do not need
`rde2util.Meta` or a v1 object adapter.

Read `tasksupport/default_value.csv` (`key,value` rows), which v1 read with
`rde2util.get_default_values`, with `read_key_values(path)` (#629). By default
it detects the encoding with chardet as v1 does and keeps every value a string,
so the result equals `get_default_values`. Merge it with the measured values for
`build_meta`:

<!-- test: read-key-values -->
```python
from rdetoolkit.nodes import build_meta, read_key_values

defaults = read_key_values(paths.tasksupport / "default_value.csv", missing_ok=True)
metadata = build_meta({**defaults, **measured}, paths.tasksupport / "metadata-def.json")
```

`key=` and `value=` name the columns and `encoding=` sets the encoding. chardet
can misdetect a short, mostly ASCII Shift-JIS file, as in v1; pass
`encoding="cp932"` for such files. A missing file raises `FileNotFoundError`;
with `missing_ok=True` it returns an empty dict.

Values may be keyed by the definition key or by its `originalName`. As in v1
`Meta.assign_vals`, the definition key wins when both spellings are present,
and `originalName` is read only when the definition key is absent (a key that
is present with `None` is excluded without falling back). Code that preferred
the `originalName` spelling should map those values onto the definition keys
first, or choose `match="original_name"` to use the declared alias exclusively
(definitions with an absent or `null` alias still use their key; an explicit
empty-string alias remains a valid source key). Use `match="key"` to
disable aliases entirely; the default `match="both"` keeps the precedence above.
`save_meta` writes four-space indentation like v1 `Meta.writefile`;
pass `indent=` to choose another.

The second argument may also be a definition Mapping. Filter a shared definition
in memory and pass it directly to `build_meta`; no temporary JSON file is needed.
String values are stripped before checking emptiness. For both `""` and
whitespace-only inputs, `build_meta` applies the following policy:

| Schema type | Default | `keep_empty_strings=True` |
|---|---|---|
| `string` | Omit the value | Keep `""` if the format permits |
| `number`, `integer`, `boolean` | Omit before conversion | Raise `StructuredError` (`ecode=1`) |

The same policy applies to repeated cells without removing their row positions.
Nonempty invalid typed values still raise conversion errors in either setting.
This normalization is specific to `build_meta`: v1 `Meta.assign_vals` and
`parse_invoice_meta` retain their existing rules, including conversion errors
for whitespace-only number, integer and boolean values.

To update `invoice.custom` as v1 `castval` / `_assign_invoice_val` did, use
`set_custom_fields(invoice, updates, schema=...)` (#603). It returns a new
`InvoiceData`; each value is cast by the field's `type` and `format` in
`invoice.schema.json`:

| Schema | Accepted values | Stored value |
|---|---|---|
| `integer` | digits with an optional unit (`"12 mm"`), an integral float (`3.0`) | `int` |
| `number` | numeric text with an optional unit | `int` when integral, else `float` |
| `boolean` | `"true"` / `"false"` (any case), other values by truthiness | `bool` |
| `string` + `date` / `date-time` / `time` | text dateutil can parse, `date` / `datetime` objects | `2023-07-19` / ISO 8601 / `13:04:05` |
| `string`, other or no format | anything | unchanged |
| any type | `None`, NaN, `NaT`, `pd.NA` (NumPy NaN / NaT included) | `None` |
| any type | `""` or whitespace only | not applied: the key keeps its value (#619) |

Blank cells read with `dtype_backend="numpy_nullable"` (`pd.NA`) are also stored as `None`. NumPy
scalars (such as `np.int64`) are cast as the equal Python value, so the result saves with `save_invoice`.

An empty or whitespace-only string, such as a blank cell read with
`read_excel(..., dtype=str, keep_default_na=False)`, is not applied: the key keeps
its current value in `custom` or stays absent, as `build_meta` omits empty strings.
`keep_empty_strings=True` casts it like any other value: a `string` field without
a date format stores it, and `integer` / `number` / `boolean` and the date formats
raise the type mismatch.

A `string` field without format keeps a non-string value as given, as v1 `castval`
did. Such a value fails the invoice validation after processing
(`1.5 is not of type 'string'`, ErrorCode 4001), so convert it deliberately. To
keep the digits as entered (`1.50`), read the cell as text
(`read_excel(..., dtype=str)` / `read_csv(..., dtype=str)`): `str(1.5)` gives `1.5`.

An undeclared key raises `StructuredError` with code 4011
(`InvoiceCustomKeyUndefined`); a value that does not fit raises `StructuredError`
(code 1) with v1's message. The injected invoice carries
`tasksupport/invoice.schema.json` in every mode, so `schema=` is needed only to
cast with a different schema (#620). Write the result with
`save_invoice(invoice, out)`. To fill values from spreadsheet columns,
`resolve_custom_key(schema, label)` returns the key whose `label.ja` or
`label.en` equals the label (`lang="ja"` or `"en"` restricts the language). An
unknown label raises `StructuredError` with code 4012 (`InvoiceCustomLabelUnknown`),
and a label shared by two fields code 4013 (`InvoiceCustomLabelAmbiguous`). These
three codes carry their remediation in the message and keep their code when the
flow declares `error_code=` (#621).

<!-- test: ga603-custom-fields -->
```python
from rdetoolkit.nodes import resolve_custom_key, set_custom_fields
from rdetoolkit.types import InvoiceData

schema = {"properties": {"custom": {"properties": {
    "measured_date": {"type": "string", "format": "date", "label": {"ja": "測定日", "en": "Measured date"}},
    "cycles": {"type": "integer", "label": {"ja": "サイクル数", "en": "Cycles"}},
}}}}
invoice = InvoiceData(raw={"custom": {"measured_date": None, "cycles": None}}, schema=schema)
row = {"測定日": "2023/07/19", "Cycles": "12"}
updates = {resolve_custom_key(schema, label): value for label, value in row.items()}

assert invoice.raw["custom"] == {"measured_date": "2023-07-19", "cycles": 12}
```

For file and image artifacts, `read_excel` accepts worksheet, header, row and
column selections; `save_csv` accepts precision, header and index options.
`save_csv(..., preamble=...)` writes a block of lines before the table, such as
the `#title` / `#legend` header `rdetoolkit.graph` reads: rows (which may differ
in length) are written in the table's CSV format, a str is written verbatim, and
`blank_line_after_preamble=True` adds one empty line before the table.
`save_json` and `save_text` accept an output `kind`. Use `read_json` for detected
encoding, `save_invoice` for the tile invoice formatting contract, and
`save_figure` for caller-owned matplotlib figures. `plot_lines` accepts x/y
columns or independent pairs, labels, title, scale, legend, size, DPI and kind.
Pairs may be `(x, y, label)`, or `labels=` names every series; `grid=True` draws
the grid, and axis-label sizes follow matplotlib rcParams unless
`label_fontsize` is set. Axis ranges, as in v1 `csv2graph(..., xlim=..., ylim=...)`
or `ax.set_xlim` / `ax.set_ylim`, are `xlim` / `ylim`, and `xscale` sets the x
axis scale; a `None` bound stays automatic, so `ylim=(0, None)` starts the axis
at 0. Series with their own x values and length, such as the regions of a
multi-region measurement, can be passed as a list of data frames: the x/y or
pair selection applies to each frame, and `labels=` names the series in frame
order (no `pd.concat(axis=1)` into one frame is needed).
Both plot nodes save with a tight bounding box by
default: pass `bbox_inches=None` to reproduce a plain v1 `fig.savefig(path)`, or
`pad_inches=0` for `savefig(path, bbox_inches="tight", pad_inches=0)`.
For an interactive chart, `save_html_figure(fig, out, "chart.html")` writes a
plotly figure with `plotly.io.to_html` under `structured/` by default, loading
plotly.js from the CDN (`include_plotlyjs=`, `full_html=` and `kind=` change
that). Its chart `<div>` id is derived from the filename rather than plotly's
random one: the sanitized stem plus a short hash of the filename
(`plotly-chart-3e67baf8`), so the file is identical on every run and fragments
of different files (`full_html=False`) keep distinct ids on one page. Pass
`div_id=` to choose it. plotly comes from the optional `rdetoolkit[plotly]` extra and is
imported only when the node runs.
Templates that select rows by cell colour use
`read_excel_fills(path, column="A", ...)` with the same sheet and row options as
`read_excel`; it returns one fill colour (ARGB hex, `theme:<n>` or `None`) per
data-frame row. `OutputContext` has no run-scoped temp directory (v1
`resource_paths.temp`); use `tempfile.TemporaryDirectory()` for scratch files,
which are removed when the block ends.
To build the main image from an uploaded PDF or SVG, as the v1
simple-registration template does, use
`render_png(source_path, out, filename, *, kind="main_image", page=1, dpi=350)`.
A `.pdf` file has that page rendered at `dpi`, a `.svg` / `.svgz` file is
rendered at its own size, and any other file is converted with Pillow like
`to_png`. The defaults (page 1, 350 dpi) match the v1 template. PDF and SVG
need `pip install 'rdetoolkit[render]'`, and SVG also needs the Cairo system
library; without them the node raises an `ImportError` that names the extra
and the library. PDF pages are rendered with pypdfium2 instead of v1's
pdf2image (poppler), so the pixels can differ from v1.

`to_png` and `to_jpeg` take `kind=` (default `other_image`); turn a TIF upload
into the main image with `to_png(path, out, "main.png", kind="main_image")`.
Copy images and attachments that are registered unchanged with
`copy_file(src, out, filename, kind=...)`, a byte-for-byte copy into any
output directory such as `struct`, `other_image`, `thumbnail` or `attachment`.
Save NumPy arrays and Pillow images, such as analysis overlays and masks, with
`save_image(image, out, filename)`; the filename suffix selects the format and
the default directory is `other_image`. OpenCV arrays are BGR: pass
`channel_order="bgr"` to get the image `cv2.imwrite` writes.
Read a text file as lines with `read_lines(path)`, which decodes like
`read_text` and returns the lines of `f.read().splitlines()`
(`keepends=True` keeps the line endings). Code that called the v1 encoding
helper directly can use `detect_encoding(path)`, the rule the builtin readers
apply. `list_excel_sheets(path)` lists the sheet names, so a sheet whose name
contains a word can be found and passed to `read_excel(path, sheet_name=...)`.
`unzip_inputs` extracts tar archives (`.tar`, `.tar.gz`, `.tar.bz2`,
`.tar.xz`) as well as ZIP. ZIP member names without the UTF-8 flag are
restored as CP932, so file names can differ from v1 code that called
`ZipFile.extractall`, which kept the cp437 names.
Programs that write the `_feature` metadata into the invoice description
themselves can use `describe_features(invoice, metadata, metadef_path)`: it
returns the invoice with the lines the Runner's `feature_description` appends
to `basic.description`. When a flow saves that result with `save_invoice`, set
`system.feature_description: false` in `rdeconfig.yaml` so the lines are not
appended twice.

To run an external converter, as v1 templates did with `subprocess.run`, use
`run_program(args, ...)` (#630). The converter writes into directories you pass
as arguments, such as `out.struct` and `out.logs`. Output streams are captured
and returned in a `CompletedProgram` (`args`, `returncode`, `stdout`, `stderr`,
`duration` in seconds). A non-zero exit, a program that cannot start, or a
`timeout` is a `StructuredError` with `error_code` (default 1) instead of
ErrorCode 3001. `error_message` replaces the default message, which names the
command line, the exit code, the run time and the last stderr lines; the command
line and the outcome are also logged. `env` adds to the inherited environment.
For a Windows converter, `wine="auto"` prefixes `wine` outside Windows and writes
`Path` arguments in Windows form (`/data/structured` becomes
`Z:\data\structured`). Convert a path inside an option string with
`to_wine_path`, for example
`f"-OutputFolder:{to_wine_path(out.struct)}"`. Text arguments are passed
unchanged.

<!-- test: ga630-run-program -->
```python

    export = Path(struct) / "export.txt"
```

To write a processing log as a tile artifact, as v1
`rdelogger.get_logger(name, file_path=Path(resource_paths.struct, "structured_log.txt"))`
did, use `artifact_logger(out, filename, name=..., kind="struct")` as a context
manager (#631). It adds a file handler to the `name` logger for the block and
removes it when the block ends, also when the block raises. Only records logged
inside the block reach the file, so a logger shared by the module never writes
one tile's lines into the next tile's file. The call is a node call, recorded in
the call log and in the RunReport `node_calls`.

- Lines use the v1 format `%(asctime)s - [%(name)s](%(levelname)s) - %(message)s`; pass `fmt=` to change it.
- An existing file is appended to (`mode="a"`, as in v1); `mode="w"` truncates it at the first record.
- No file is created when nothing is logged (as in v1).
- Records below `level=` (default `DEBUG`) are not written. A logger whose own level is higher is lowered for the block and restored afterwards.
- To keep the ERROR line of a failure, log it inside the block with `logger.exception(...)` and re-raise.
- A record logged in the context that entered the block (the tile's code and the nodes it calls) is written to that block's file only. Runners that use the same logger concurrently in one process do not mix their lines.
- A record logged in a context that is inside no block, such as a worker thread started inside the block, is written to every block active on that logger.
- Records from other processes are never written, also from a worker forked inside the block that keeps running after it.
- When blocks overlap, the logger level returns to its value before the first block once the last block ends.
- Without `name`, the logger is named after the filename without its suffix.

`unzip_inputs` returns absolute paths to extracted files in archive order.
Directory entries and unsafe destinations are excluded; repeated archive members
produce repeated paths. Existing containment checks, including outward symlinks,
still apply. Callers that ignored the old return value can keep doing so.
Pass `include_dirs=True` to also receive directory entries, including empty
directories, when listing the archive structure.

Before a flow runs, the Runner copies the tile's input files into `raw/` when
`system.save_raw` is on and into `nonshared_raw/` when
`system.save_nonshared_raw` is on, as v1 did before the dataset callback.
Templates that removed or replaced such a copy use
`remove_raw_copy(out, config, filename)` and
`replace_raw_copy(out, config, filename, members)` (#623). Use
`remove_raw_copy` when an uploaded `*_meta.json` is saved under `meta/` and
must not stay as raw data, and
`replace_raw_copy(out, config, archive.name, unzip_inputs(archive, tmp))` when
the extracted files, not the ZIP, are the raw data. Both nodes act on the
enabled kinds only (a disabled kind is not touched), and the call is recorded
in the call log. `replace_raw_copy` copies the members by name (archive
subdirectories are not kept) and then removes the original copy. A missing
copy, two members with the same name, a member that would overwrite
another input's copy, or a member that is the copy being replaced or lies
inside it raises an exception and changes nothing. Replace code
that deleted a copy directly, such as
`out.path_for("nonshared_raw", name).unlink()`, with these nodes.


### Load settings and override the mode in main.py

To prepare configuration before entering a flow, use
`rdetoolkit.runner.load_run_config(root=None, *, overrides=None)`.
`root` accepts a project or data directory as a `Path` or string and defaults to
the current directory. The helper uses the Runner's data-root resolver and
discovery order: project-root `rdeconfig.yaml`, project-root `pyproject.toml`,
then `tasksupport/{rdeconfig.yaml,rdeconfig.yml,pyproject.toml}` under the resolved
data root. Tasksupport files are interpreted as v1 configuration (Design §6.3).

`overrides` merges recursively over the discovered settings. Pass the returned
`RdeConfig` to `run(flow=..., config=...)` to use the entire object as the
configuration. Passing a mapping directly also overrides discovered settings.
This example changes the mode while retaining other tasksupport values.

<!-- test: load-run-config -->
```python
from rdetoolkit import flow, workflows
from rdetoolkit.runner import load_run_config
from rdetoolkit.types import RdeConfig


@flow
def pipeline(config: RdeConfig) -> None:
    print(config.system.extended_mode)


config = load_run_config(overrides={"system": {"extended_mode": "MultiDataTile"}})
report = workflows.run(flow=pipeline, config=config)
if report.status != "success":
    raise SystemExit(1)
```

`RdeConfig.model_validate({"system": {"extended_mode": None}})` is also accepted.
YAML `null` and a `None` override normalize to an unset mode with the default
value `"invoice"`. SmartTable / ExcelInvoice detection then emits no W1001.
For v2 flows, a conflicting mode explicitly set as a string raises a catalogued
configuration error. Only the v1 callback entry retains the detection override
and W1001 (Design §6.2).

After validation, `config.system.extended_mode` is always a `str`. An unset
mode and an explicit `"invoice"` stay distinct through mode resolution,
`config_digest`, and `repro` export → import → run. To leave the mode unset in
typed Python code, omit the argument rather than calling
`V2SystemSettings(extended_mode=None)`. Pass `None` only in mappings
(`load_run_config(overrides=...)` or `RdeConfig.model_validate(...)`), or write
`null` in YAML. Type checkers report `extended_mode=None` as an `arg-type` error.

### Template settings {#template-settings}

In v2, settings that belong to your template, not to rdetoolkit, live under
`custom:`. Many v1 templates instead keep them in a top-level section of
`tasksupport/rdeconfig.yaml`, next to `system:`. v2 reads such a section as
`config.custom["<section>"]` without a warning, so an unchanged template keeps
working. This is a v1-form `tasksupport/rdeconfig.yaml`:

<!-- test: template-settings-v1 -->
```yaml
system:
  extended_mode: null
sem:
  magnification_key: Mag
  thumbnail: true
```

A flow reads it as `config.custom["sem"]["magnification_key"]`. When the
section and `custom:` both define the same name, `custom:` wins. A top-level
value that is not a mapping (for example `vendor: acme`) is also kept under
`custom`, but it warns and asks you to move it under `custom:`. A section
named like a v1 section, such as `sytem:`, also warns and names the section it
resembles: its settings are kept under `custom` and are not applied.

A project-root `rdeconfig.yaml` or `[tool.rdetoolkit]` is the v2 form and
rejects unknown top-level sections (E1002), so a typo such as `sytem:` fails
there. In a project-root `rdeconfig.yaml`, write the same settings under
`custom:`:

<!-- test: template-settings-v2 -->
```yaml
custom:
  sem:
    magnification_key: Mag
    thumbnail: true
```

## Runtime changes

In a production `main.py`, opt into nonzero exits for failed or partial runs.
The run report, `job.failed` on failure, and completed artifacts are finalized
before exit. A success returns normally; failed exits with 1 and partial with 2.
The default library call still returns a `RunReport` for inspection. Its public
`exit_code` property uses the same mapping as the CLI and can also be passed to
`SystemExit`; it is derived and adds no JSON field or schema version.

<!-- test: ga572-main -->
```python
from rdetoolkit import workflows
from processing import pipeline

workflows.run(flow=pipeline, exit_on_failure=True)
```

Template discovery imports skeleton providers declared in root Python modules
and the conventional `modules/` package when `--module` is omitted; installed
plugins remain discoverable. Use `--module` to select other provider modules.
Template descriptions include slot documentation and domain annotations while
omitting standard library types. Processing-template init generates `main.py`,
the implementation and a test skeleton; all three have overwrite protection.
Slot signatures must still match exactly, including parameter names and kinds.
Add optional hooks when evolving a published skeleton; adding a required slot
requires updating its concrete implementations. The depth-2 and flow-boundary DI
rules remain unchanged (Design §5.2).

`migrate apply` preserves unsupported cross-module entries and helper files,
and reports the callback requiring manual migration. Convert that callback and
its entry together. Supported local callbacks preserve comments and literals;
removal of the legacy entry is explicitly reported with the flow CLI invocation.

- A v1 `main.py` that rewrites `data/inputdata/` before calling `run()`
  (splitting a concatenated instrument file, building a SmartTable CSV and its
  zip) declares that step with the flow decorator's `prepare=prepare_inputs`
  option, with
  `def prepare_inputs(inputdata: Path, config: RdeConfig) -> None`. The Runner
  calls it once per run, after loading the configuration and before resolving
  the mode, so both `workflows.run(flow=...)` and `rdetoolkit run <pkg.mod:flow>`
  see the prepared inputs. Without it, `rdetoolkit run` resolves the mode from the
  unprepared files. `--validate-only` also runs it, so the pre-flight checks
  the same mode as the real run but may modify `inputdata/`; write it to be
  idempotent (a re-run and `rdetoolkit repro` see the already-prepared
  inputs). It receives a copy of the configuration. It is recorded as
  `prepare.started` / `prepare.completed` / `prepare.failed` events. The
  flow's `error_code` / `error_message` options apply to its failures as to
  the body's; without them an ordinary exception fails the run with 3001
  before any tile. A `StructuredError` keeps its own code and message. Only
  the flow the Runner executes is prepared (a nested flow's `prepare` is not
  run), and direct calls of the flow do not run it.
- Use the flow decorator with `error_code=7, error_message="Cannot process input"` to map body (and prepare)
  failures to one code and message through either v2 entry. Supplying only a
  code preserves the original message; supplying only a message uses 3001.
  The message may contain `{error}` (the exception's text) and `{error_type}`
  (its class name), e.g. `error_message="Cannot read sample: {error}"`; other
  braces are kept as written.
  A `StructuredError` raised in the body keeps its own code and message, as
  with v1 `catch_exception_with_message`.
  Direct function calls still propagate the original exception. The original
  exception remains chained in Runner failures; process-control exceptions
  such as `KeyboardInterrupt` and `SystemExit` are not mapped.
- **When rewriting v1 `catch_exception_with_message` as a flow, set `error_code=1` explicitly.**
  The v1 decorator turns a plain exception into a `StructuredError` with
  `ecode=1` and an `Error: ` prefixed message. Moving only `error_message` to
  the flow decorator uses 3001, so the `job.failed` `ErrorCode` changes from 1.
  The mapping that reproduces the v1 result is:

  | v1 `catch_exception_with_message` arguments | flow decorator arguments |
  |---|---|
  | `error_message="m"` | `error_code=1, error_message="Error: m"` |
  | none | `error_code=1, error_message="Error: {error}"` |
  | `error_code=c, error_message="m"` | `error_code=c, error_message="Error: m"` |

  If you do not need the `Error: ` prefix, `error_code=1, error_message="m"`
  and, without arguments, `error_code=1` alone keep the same code (the
  message is then `m` or the exception's text respectively).
- **`catch_exception_with_message` is deprecated.** Applying it emits a
  `DeprecationWarning`; its behavior is unchanged and it is not removed in v2.
  When the `job.failed` `ErrorCode` must stay at its v1 value, rewrite it with
  the table above. Otherwise raise `ProcessingError` for failures the user
  should see and drop the decorator. You choose no error code: the Runner
  writes it to `RunReport`, the iteration log and `job.failed` as 3007
  `ProcessingFailed`, with `Remediation: <guidance>` appended to the message.
  Without `remediation` the catalog default is used. `raise ... from exc` keeps
  the original exception. Ordinary exceptions such as `ValueError` stay 3001.
  The example below replaces the `FileNotFoundError` of a missing file with a
  `ProcessingError`.

<!-- test: processing-error -->
```python
from pathlib import Path

from rdetoolkit.exceptions import ProcessingError


def read_sample(path: Path) -> str:
    try:
        return path.read_text(encoding="utf-8")
    except FileNotFoundError as exc:
        raise ProcessingError(
            "Input file was not found.",
            remediation="Check that the file is in inputdata.",
        ) from exc


try:
    read_sample(Path("missing.csv"))
except ProcessingError as error:
    caught = error

assert caught.code == 3007
assert isinstance(caught.__cause__, FileNotFoundError)
```

  Neither the flow's `error_code` / `error_message` nor
  `catch_exception_with_message` remaps a `ProcessingError`; it keeps 3007 and
  its remediation.
- `InputPaths` injected into a flow uses paths relative to the working directory,
  like v1 input paths. Path-based user error messages therefore keep the v1
  spelling. The Runner still resolves the data root once for its internal work.
- The canonical v2 return value is `RunReport`. Start from `report.status` and
  `report.iterations`.
- **On the flow entry point, `on_iteration_error` defaults to `continue`.** If you
  need v1's immediate stop (fail-fast), set `fail_fast` explicitly. The v1 entry
  point `run(custom_dataset_function=...)` keeps v1's iteration rules (see
  "Intentional differences" below).
- The graph is a call sequence recorded after execution, not a pre-execution DAG.
  Ordinary Python control flow works as is.
- MultiDataTile assigns its tiles (`data/`, `divided/0001`, ...) in file name order,
  as v1's MultiDataTile did. A v1 structured program that listed `inputdata` itself,
  such as `for f in inputdata.glob("*")`, got directory order instead. To keep that
  order, set `multidata_tile.order: filesystem` (the default is `name`). The listing
  order depends on the filesystem (#597).

## Compatibility scope and schedule for v1 users

This section is final as of 2.0.0rc1. The v1 execution path (the iteration loop
and the per-mode processing) has been removed and every entry point runs through
a single Runner. The v1 **contract** (entry point, artifacts, how a run ends) is
protected by tests that compare against contract snapshots frozen from the v1 execution path carrying the v1.7.1 contract.

### What is kept

- **Entry point**: the signature of
  `rdetoolkit.workflows.run(custom_dataset_function=...)`. The callback still
  receives `(srcpaths, resource_paths)`.
- **The v1 contract**: the returned JSON (the per-tile status list),
  `SystemExit(1)` on failure, fail-fast by default, the `data/job.failed` format,
  the output directory layout (`raw/`, `structured/`, `divided/NNNN/` and so on),
  and `data/logs/rdesys_<timestamp>.log`.
- **Tier 1 API**: `rdetoolkit.models.rde2types`, `rdetoolkit.rde2util`,
  `rdetoolkit.invoicefile`, `rdetoolkit.errors`, `rdetoolkit.exceptions`,
  `workflows.check_files` / `check_files_result`, and
  `workflows.generate_folder_paths_iterator`.
- The v1 CLI commands: `rdetoolkit init` and `rdetoolkit validate` keep their names,
  and the renamed v1 commands keep working in v2.0.x as deprecated aliases (see
  [CLI command renames](#cli-command-renames)).

### What was removed (2.0.0rc1)

- The `rdetoolkit.modeproc` module.
- The `rdetoolkit.processing` package (`Pipeline`, `ProcessingContext`,
  `Processor` and all of its subclasses).
- The per-mode functions in `rdetoolkit.workflows`: `invoice_mode_process`,
  `excel_invoice_mode_process`, `multifile_mode_process`,
  `rdeformat_mode_process` and `smarttable_invoice_mode_process`.
- The public `impl` and `interfaces` exports of the `rdetoolkit` package. Both
  modules remain as internals of the Runner but are not public API.

Code that imports any of these directly should go back to calling
`run(custom_dataset_function=...)` or move to a flow function.

**Deprecated (no caller left, kept only for compatibility)**:
`rdetoolkit.errors.handle_and_exit_on_structured_error` and
`rdetoolkit.models.result.WorkflowResultManager`. Do not use them in new code.
The `smarttable_rowfile=` argument of `RdeOutputResourcePath` also remains, as in
v1.7, a deprecated alias of `smarttable_rawfile`.

### What was removed (after 2.0.0rc1, before GA)

- The package-embedded AI-agent guide added in v1.6.0:
  `rdetoolkit.get_agent_guide()`, the `agent-guide` CLI command, the
  private `rdetoolkit._agent` module with its bundled Markdown, and the
  package-local `.agents/` guidance. The installed package no longer ships
  agent-facing documents, and there is no replacement API. Remove calls to it
  from code and scripts (#644). Agent guidance for v2 is published as a
  separate, version-matched [Agent Skills pack](usage/agent_skills.en.md).
- The draft error taxonomy of the v2 prereleases: the string
  `rdetoolkit.errors.ErrorCode` enum (`E001`-`E025`), `RdeGraphError`,
  `RdeCompileError`, `RdeIOError`, `UnconnectedInputError`, and the `E_CYCLE` /
  `E_UNCONNECTED_INPUT` / `E_DUPLICATE_ID` / `E_AMBIGUOUS_DEPENDENCY`
  constants. They appeared only in the 2.0.0a1 / 2.0.0rc1 prereleases, never
  in v1. Use the `RdeError` subclasses (`RdeConfigError`, `RdeRegistryError`,
  `RdeExecutionError`, `RdeValidationError`, `RdeInternalError`) with an int
  code from `ERROR_CATALOG` (#646).

### Behaviour changes

**Introduced in the v1.7 line (unchanged in v2)**

- In SmartTable mode the row CSV (`fsmarttable_*.csv`) is not part of `rawfiles`
  (#503). Use `smarttable_rawfile` when you need the row CSV (the old name
  `smarttable_rowfile` was a misspelling and has been renamed).
- With `smarttable.save_table_file: true` the original SmartTable file is
  registered first, as `divided/0001`, and the data rows move to `divided/0002`
  onwards (#503).
- A SmartTable `meta/<key>` column requires `tasksupport/metadata-def.json`.
  Without it the run fails with `StructuredError` instead of silently ignoring
  the column (#496).

**Introduced in 2.0.0rc1**

- Every run writes an event log, `data/logs/events_<run_id>.jsonl`, by default.
  The file is capped at 64 MiB per run: when the cap is reached, warning **W1002**
  (`EventsLogTruncated`) is recorded once and only the node-level events after
  that point are dropped (run-level and tile-level events and warnings are
  kept). `data/logs/**` is not part of the v1 artifact contract.
- `data/logs/iterations/` is emptied when tile iteration starts. `job.failed`,
  `run_report_*` and `events_*` are kept across runs, as before.

**Introduced in 2.0.1: `templates/` is renamed to `template/`**

- `rdetoolkit init` generates `template/tasksupport/` instead of
  `templates/tasksupport/`, so all generated directories (`container/`,
  `input/`, `template/`) have singular names.
- A project created by v1 still has `templates/tasksupport/`. Run
  `rdetoolkit migrate apply <project>` on the project root. The dry run lists
  the `templates/` → `template/` move next to the Python conversions. With
  `--no-dry-run`, the output directory (`--out`, or `<name>_migrated`) contains
  `template/`; the input directory is not changed. `migrate check <project>`
  reports `templates/` as a finding.
- If the project has both `templates/` and `template/`, `migrate apply` stops
  with exit code 3 and does not merge them. Move the files you want to keep
  into `template/`, remove `templates/`, and run it again.
- Until you migrate, `validate all` reads `templates/tasksupport/` when
  `template/tasksupport/` does not exist and reports a `deprecated_layout`
  warning. The warning does not change the exit code, but `--strict` fails on it.
- `init` run in a directory that has `templates/tasksupport/` does not create
  `template/`. It prints a warning that points to `migrate apply`.
- `migrate apply` renames only the directory. Update paths you wrote yourself,
  such as `[tool.rdetoolkit.init]` entries in `pyproject.toml` or CI scripts
  that copy schemas into `templates/tasksupport/`.

### Intentional differences (cases where v2's result differs from v1)

A header-only Excel invoice is rejected before tile execution. The compatibility
callback entry preserves v1's generic failure (999); the flow entry reports
the input validation error `EmptyExcelInvoice` (4004), with guidance to add data
rows. A workbook missing its invoice sheet keeps its existing error contract.

| Case | v1 | v2 |
|---|---|---|
| The callback raises `StructuredError(msg, ecode)` | `ecode` and `msg` in `job.failed` | Same |
| The callback raises a plain exception | `ErrorCode=999`, `Unexpected error in <mode> mode: ...` | `ErrorCode=3001`. The message is the error-catalogue E3001 text and contains your exception's message |

### csv2graph / Graph Engine

Every intentional behaviour change of the graph entry points has a stable id, IC-1 to
IC-16. The tables below are grouped by topic, and the rows of each table are ordered by
id. The spec-first API (`render_graph`, `GraphSpec`, custom readers and renderers) is
described in [Graph Engine](usage/structured_process/graph_engine.en.md).

`csv2graph`, `plot_from_dataframe` and `rdetoolkit plot` validate the request before
any figure is drawn. The requests below raise `PlotRequestError`, which is a
`PlotConfigError` and also a `ValueError`, so existing code that catches `ValueError`
keeps working; its `reason` attribute tells the cases apart. The error is raised
before any file or directory is created. The CLI reports the same conditions as a
usage error with exit code 2.

| Id | Change | v1 | v2 | What to do |
|---|---|---|---|---|
| IC-1 | `mode` is neither `"overlay"` nor `"individual"` (including a different case or `"dual_axis"`) | Plotted as individual figures | `PlotRequestError` (`reason="invalid_mode"`) | Pass a valid `mode` |
| IC-2 | `mode="individual"` together with `no_individual=True` (`--mode individual --no-individual` on the CLI) | Finished without writing anything | `PlotRequestError` (`reason="contradictory_switches"`); exit code 2 on the CLI | Drop one of the two |

A table without columns still raises `ColumnNotFoundError`, and a table without a
y series still raises `ValueError`, as before.

Individual figure file names are reserved for every series before the first figure is
drawn, so no artifact of a run overwrites another one:

| Id | Change | v1 | v2 | What to do |
|---|---|---|---|---|
| IC-3 | Two series whose individual file names differ only by case, spacing or Unicode normalization (for example `Voltage` and `voltage`, or `A B` and `A_B`), or a header containing `/`, `\` or `..` | The later figure overwrote the earlier one; an unsafe header failed after the overlay image was written | Every colliding series gets its series id appended (`plot_voltage_s000.png`, `plot_voltage_s001.png`) and a `GraphUserWarning` is emitted; unsafe characters become `_`. Names that do not collide are unchanged | Rename the columns if you need specific file names |

Axis limits are validated by one rule shared by `csv2graph`, `plot_from_dataframe`,
`rdetoolkit plot` and `GraphSpec` (`AxisSpec.limits`). A `None` side keeps the
automatic limit, so `xlim=(0, None)` fixes only the lower bound. Reversed bounds
(`min > max`) are still accepted and invert the axis. On the CLI, `--xmin`, `--xmax`,
`--ymin` and `--ymax` set one side each; combining one of them with `--xlim`/`--ylim`
on the same axis is a usage error (exit code 2). The same table lists the changes to
Matplotlib style and figure ownership (IC-5), mixed-unit overlays (IC-6), dual-axis
plotting (IC-7) and the figure size and style options (IC-10).

| Id | Change | v1 | v2 | What to do |
|---|---|---|---|---|
| IC-4 | One-sided `xlim`/`ylim` such as `(0, None)` or `(None, 10)`; limits with a non-finite bound, equal bounds, or a bound `<= 0` on a log axis (`logx`/`logy`) | One-sided limits were dropped (both sides automatic); invalid limits were passed to Matplotlib, which ignored them with a warning | The given side is applied and the other side stays automatic; invalid limits raise `PlotRequestError` (`reason="invalid_axis_limits"`) naming the axis and the bound, before anything is written; exit code 2 on the CLI | Omit the limit to get the old fully automatic result; pass positive bounds on a log axis |
| IC-5 | Matplotlib style and figure handles after `csv2graph`, `plot_from_dataframe` or `rdetoolkit plot` | The graph style (`font.size` 20, inward ticks and more) stayed in the process-wide `rcParams` and changed later plots; every figure stayed open, also after a failed save | The style applies only while the figures are drawn and saved, and `rcParams` are unchanged afterwards. Saved figures are closed, also when writing fails. Figures returned with `return_fig=True` stay open, belong to the caller (close them with `plt.close`) and have their layout frozen; saved at 300 dpi they match the previous image. The backend is never switched | Call `apply_matplotlib_config()` before plotting if later plots relied on the old global style |

Renderers are replaceable. Pass a `RendererRegistry` as `renderers` to `render_graph` and every artifact goes to the first registered renderer whose `RendererCapabilities` declare its format and figure kind. Any object implementing the `GraphRenderer` protocol (`capabilities`, `render`, `export`, `close`) can be registered, without changing rdetoolkit internals. With `html=True`, `csv2graph` and `plot_from_dataframe` also check for Plotly before drawing anything. Without Plotly they already failed with an `ImportError` before writing any file, so code catching `ImportError` keeps working.

### Diagnostics and legacy tracebacks

For v2 troubleshooting, with or without a coding agent, use
`rdetoolkit report diagnose <run_report.json> --json`. Its versioned envelope
leaves out exception text, locals, environment values and input paths (see
[Diagnostic commands](usage/diagnostics.en.md)). The legacy traceback API
(`handle_exception`, `CompactTraceFormatter`, `SecretsSanitizer`,
`Config.traceback`, `TRACE_VERBOSE` / `TRACE_FORMAT`) is unchanged and raises no
new deprecation warning; its `<STACKTRACE>` output is kept for local use on the
v1 callback entry and is no longer the recommended format to hand to an agent.
Name-based masking is not anonymisation. See the
[compatibility matrix](usage/structured_process/traceback.en.md).

`repro export` archives now come in two kinds: the full archive, which holds
your raw inputs and needs a review before it leaves your machine, and
`--manifest-only`, which holds digests and diagnostics and cannot be replayed.
`repro export` no longer replaces an existing `-o` file, and `repro import`
refuses unsafe or inconsistent archives (see
[repro](usage/cli.en.md)). Nothing is uploaded automatically.

### Rollback

If v2 causes problems, pin `1.7.1`, the latest v1 release (for example
`rdetoolkit==1.7.1` in `requirements.txt`). The development build that still
contains the old execution path is not on PyPI; it can only be installed from
source at the git tag `v2.0.0a1` (for diagnosis only; that tag reports
`__version__` as `2.0.0`).

### Schedule

Releases go `2.0.0rc1` → GA `2.0.1`. The version number `2.0.0` is skipped and
will not be published as a final release.

## Registration mode selection and reproduction

V2 flow execution now treats `system.extended_mode` as registration intent.
Use the canonical names `invoice`, `multidatatile`, `smarttable`,
`excelinvoice`, and `rdeformat`. The exact legacy aliases `Invoice`,
`MultiDataTile`, `SmartTableInvoice`, `ExcelInvoice`, and `RDEFormat` remain
accepted. Other spellings fail with a list of valid names.

Omit the setting, or set it to null, to detect a single special table format.
An explicit `invoice` requests Invoice mode and conflicts with a SmartTable
or ExcelInvoice input. Remove the conflicting file or request its mode.
Mixed tables, duplicate workbooks, and ambiguous special archives fail before
registration. Multiple ordinary raw files still form one Invoice tile;
request `multidatatile` to register one tile per file.

The v1 callback entry preserves file-detection priority and W1001 on a
conflicting setting. A v2 flow raises a catalogued configuration error for
the same conflict. Loading a legacy-format config does not turn a flow into
a callback compatibility run.

### Templates that support more than one mode

A v1 template that sets `extended_mode: MultiDataTile` and also accepts
SmartTable uploads relied on the callback's file-detection priority. As a v2
flow, the same setting rejects every SmartTable upload with 1005. Removing the
setting makes ordinary multi-file uploads a single Invoice tile instead. Declare
both modes in the `registration` section instead, in `rdeconfig.yaml` or
`data/tasksupport/rdeconfig.yaml`, and remove `system.extended_mode`:

<!-- test: multi-mode-registration -->
```yaml
registration:
  selection: auto
  supported_modes: [multidatatile, smarttable]
  fallback_mode: multidatatile
```

A SmartTable upload then registers one tile per table row, and any other upload
registers one tile per file. The policy applies to the v1 callback entry as well,
so `main.py` needs no change unless it reads `config.system.extended_mode`. That
value is now unset (`None`) even when the run resolves to MultiDataTile, so
branch on the registration inputs instead. A top-level `registration:` section
without `selection` is still template settings under `custom`. An ExcelInvoice workbook
fails with 1009 because the template does not list it. A SmartTable table next
to an ExcelInvoice workbook fails with 1007. Keeping both `registration` and
`system.extended_mode` fails with 1002, also when one of them comes from a
`run --config` override. Such an override sets the other to null, for example
`{registration: null, system: {extended_mode: multidatatile}}`. An overriding
`registration` replaces the project's policy whole. `selection: fixed` with
`mode: <name>` is the same as an explicit `system.extended_mode`. A ZIP never
selects RDEFormat on its own. List `rdeformat` as the `fallback_mode` to
register a ZIP with RDEFormat. `rdetoolkit run --validate-only --explain`
reports the policy under `decision.selection`. The complete five-mode
compatibility and conflict matrix is in the v2 architecture guide, section 7.1.

Configuration loading and reproduction retain the exact spelling `RDEFormat`.
The callback contract interprets it as Invoice, while `rdeformat` selects
RDEFormat, so their config digests differ. A v2 flow canonicalizes `RDEFormat`
to `rdeformat` at its execution boundary. Replaying through the same entry
preserves the mode and tile count.

Config normalization and new reproduction archives retain whether invoice
was explicitly requested. Config digests now distinguish automatic selection
from explicit invoice. Archives created by earlier versions may already have
lost this information; importing them cannot recover intent that was omitted
at export. An older archive that omitted the mode, stored its default, or
conflated `RDEFormat` and `rdeformat` in the config digest can
also fail the current import's config-digest check with exit code 3. Import
that archive using the RDEToolKit version that created it. Review the recovered
`rdeconfig.yaml`, set the intended mode, then rerun with the current version
and export a new report and archive. Editing the archive's config alone does
not repair its manifest and report digests.

Use `rdetoolkit run pkg.mod:pipeline --validate-only --explain --format json` to inspect the
current inputs without running user preparation or the flow, or publishing
artifacts. The explanation includes groups, order, output paths, and mode-owned
artifact stages. Ordinary `--validate-only` retains its existing preparation
and report behavior. A preparation function can change the later run's inputs.

The five modes use the following registration groups after system files are
filtered. Tile 0 writes directly under the resolved data root; tile 1 and later
write under `divided/0001/`, `divided/0002/`, and so on. These are output tile
indices, including when an RDEFormat archive uses different directory numbers.

| Mode | Groups and order | Tile count |
| --- | --- | --- |
| `invoice` | All ordinary inputs and ZIP files form one group; ZIPs remain raw inputs. Ordinary files precede ZIPs, with filesystem order within each category. | 1, including empty input |
| `multidatatile` | One input file per group. Default `name` ordering sorts filenames; `filesystem` preserves the directory's order. | File count, or 1 empty tile |
| `smarttable` | Each data row supplies its referenced files. The last row is tile 0; earlier rows follow in table order. With `save_table_file=true`, the original table occupies tile 1 and earlier rows begin at tile 2. | Data-row count, plus 1 when saving the original table |
| `excelinvoice` | One group per workbook data row, in workbook order. Without a ZIP, groups have no raw files; one folder group may be reused for every row. File mappings must identify unique archive filenames. | Data-row count; a workbook with no data rows is rejected |
| `rdeformat` | ZIP members are grouped by the first four-digit directory component in their path. Members without one join group 0. Groups sort numerically and retain archive-member order internally. | Group count, or 1 empty tile for an empty ZIP |

When both a parent folder and its child contain files, ExcelInvoice groups
the parent first before applying workbook order, preserving the legacy
traversal and each file's corresponding invoice row.

### ExcelInvoice row-to-folder association

When rows map to archive folders (the workbook has no `data_file_names/name`
column), v2 applies the same positional rule as v1. Ambiguous identifiers
are not rejected.

1. Each folder that contains files becomes one group. Groups are ordered by
   their path components, so a parent folder precedes its children.
2. For the first file of each group, v2 takes the components of its
   archive-relative path (folder names and the file name). The group gets the
   number of the first workbook row, from the top, whose first-column value
   equals one of those components exactly (case-sensitive). A group with no
   matching row gets a number after every row.
3. Groups are stably sorted by that number. Groups with the same number keep
   the order from step 1.
4. The sorted groups are assigned to workbook rows from top to bottom.

Step 4 assigns by position. Identifiers only reorder groups, so a row whose
identifier matches a folder is not guaranteed to receive that folder.

| Identifier case | Result |
| --- | --- |
| Each group's path contains exactly one identifier, and no two groups share it | Each row receives its matching folder, also when the workbook rows are reversed |
| Identifiers are distinct, but one also appears in another group's path (an ancestor folder or a file name) | That group takes the highest row among the identifiers in its path. For `parent/root.txt`, `parent/a/a.txt`, `parent/b/b.txt` with rows `parent`, `b`, `a`, all three groups take row 1 and keep folder order, so row 2 (`b`) receives `a/a.txt` and row 3 (`a`) receives `b/b.txt` |
| No row matches | Rows receive folders in folder order |
| The same identifier appears on several rows | Groups matching it share one number and are assigned in folder order |
| A parent folder name is the identifier | A child's path also contains the parent name, so parent and child share a number. If a row naming the child is higher in the workbook, the child takes that row's number instead |
| Only some rows match | Matched groups come first and unmatched groups last, then rows are assigned by position. For folders `a` and `b` with rows `missing`, `a`, row 1 receives `a` and row 2 receives `b` |

A folder count that differs from the row count is still input validation
error 4006, except that a single folder group is shared by every row.

One difference from v1 remains. v1 also matched components of the absolute
extraction path, so an identifier equal to an extraction directory name such
as `data` or `temp` matched every group. v2 matches archive-relative paths
only, and such an identifier counts as unmatched.

Distinct identifiers alone do not guarantee the intended association. Each
row receives its matching folder only when the first file of every group has
exactly one workbook identifier among its path components, and no two groups
share that identifier. To associate rows and folders reliably, place one
folder per row directly under the archive root without nesting, and write
that folder name in the row's first column. Keep the folder names different
from every other folder and file name in the archive. Check the association
before running with the
`input_names` and `source_row` of each tile in
`rdetoolkit run ... --validate-only --explain`. The preview and the run build
the same association from the same input snapshot.

A header-only SmartTable produces no tiles unless `save_table_file=true`, in
which case its original table is tile 0. Original-table tiles register the
table without invoking the flow. These SmartTable indices preserve the RDE
registration convention in which the root tile is registered last.

V2 RDEFormat preview and execution group tiles by numeric directory and retain
archive-member order within each group. The callback route retains its legacy
filesystem ordering. MultiDataTile `filesystem` ordering explicitly reports
that its order is not reproducible; name ordering remains deterministic.

RDEFormat report `datatile_id` and `target` keep their first-input derivation.
V2 now takes that first input from archive order, so their values can differ
from the callback's filesystem-first values. Tile indices and artifact output
paths retain their existing contracts. Invalid v2 special layouts can now fail
with a planning error before extraction or missing-invoice validation; the
callback keeps its historical error priority and partial artifacts.
