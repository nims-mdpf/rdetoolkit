# Migrating from v1 to v2

The canonical v2 entry points are an eagerly executed function carrying the flow
decorator and a ProcessingTemplate. Results come back as a `RunReport`; `status`,
the per-tile results, warnings and errors are all read from that one schema. This
guide does not ask you to throw your handler classes away in one step: it combines
a mechanical conversion with a small amount of manual work.

## 1. Inspect the existing code

Take the following v1-style file as `legacy.py`.

<!-- test: legacy-source -->
```python
import rdetoolkit.workflows as legacy_workflows


class TextHandler:
    def process(self, srcpaths, resource_paths):
        source = next(srcpaths.inputdata.glob("*.txt"))
        destination = resource_paths.struct / "structured.txt"
        destination.write_text(source.read_text(encoding="utf-8"), encoding="utf-8")


def custom_dataset_function(srcpaths, resource_paths):
    TextHandler().process(srcpaths, resource_paths)


if __name__ == "__main__":
    legacy_workflows.run(custom_dataset_function=custom_dataset_function)
```

`migrate check` is a read-only command that reports migration points.
`migrate apply` is a dry run by default and prints the converted flow function.
Only after reviewing it, pass `--no-dry-run -o <another directory>`. The input
file is never rewritten in place.

<!-- test: migration-commands -->
```bash
$ python -m rdetoolkit migrate check legacy.py
$ python -m rdetoolkit migrate apply legacy.py
```

Constructs that cannot be converted, such as dynamic dispatch, are left behind as
`TODO(rdetoolkit-migrate)`. Even without a TODO, check the generated code's tests
and output directory before adopting it.

## 2. The intermediate form: wiring handlers with `as_node`

An existing handler that satisfies an Appendix M Protocol can, for the migration
period only, have a method turned into an ordinary node with `as_node`. The
Protocol helps with this migration decision; it is not a DI mechanism and not an
entry point for new designs.

<!-- test: as-node-bridge -->
```python
from rdetoolkit import as_node


class LegacyReader:
    def read(self, name: str) -> str:
        return name.upper()


read_legacy = as_node(LegacyReader(), method="read", id="docs.migration.legacy_reader")
result = read_legacy("sample.txt")
assert result == "SAMPLE.TXT"
```

The class may stay at this stage, but pass values between nodes as explicit
arguments and do not add hidden state such as `self.df`.

## 3. Choose the final form

If a domain template exists, check its slots with `skeletons show <name>` and
implement only the TODO slots of the class generated by
`new processing <name>`. The template owns the skeleton, the save
order and the output conventions.

For irregular processing without a template, write one function with the flow
decorator. `if`, loops, f-strings, literal arguments and default arguments behave
exactly as in ordinary Python. Split work into functions with the node decorator
only when you want to reuse it. Use the builtin nodes in `rdetoolkit.nodes` for
saving.

For measured metadata, use the public `build_meta(values, metadef_path)` node,
then `save_meta(metadata, out)`. The definition controls filtering, type
conversion, key order, units (including `$Key` references), and variable rows.
Use `repeated={key: values}` for repeated columns; scalar values for variable
definitions become one row. `Metadata.units` holds constant units and
`Metadata.variable` holds rows of value/unit cells. `parse_invoice_meta` applies
the same rules to the invoice's nested `custom` section. User flows do not need
`rde2util.Meta` or a v1 object adapter.

Read `tasksupport/default_value.csv` (`key,value` rows), which v1 read with
`rde2util.get_default_values`, with `read_key_values(path)` (#629). By default
it detects the encoding with chardet as v1 does and keeps every value a string,
so the result equals `get_default_values`. Merge it with the measured values for
`build_meta`:

<!-- test: read-key-values -->
```python
from rdetoolkit.nodes import build_meta, read_key_values

defaults = read_key_values(paths.tasksupport / "default_value.csv", missing_ok=True)
metadata = build_meta({**defaults, **measured}, paths.tasksupport / "metadata-def.json")
```

`key=` and `value=` name the columns and `encoding=` sets the encoding. chardet
can misdetect a short, mostly ASCII Shift-JIS file, as in v1; pass
`encoding="cp932"` for such files. A missing file raises `FileNotFoundError`;
with `missing_ok=True` it returns an empty dict.

Values may be keyed by the definition key or by its `originalName`. As in v1
`Meta.assign_vals`, the definition key wins when both spellings are present,
and `originalName` is read only when the definition key is absent (a key that
is present with `None` is excluded without falling back). Code that preferred
the `originalName` spelling should map those values onto the definition keys
first, or choose `match="original_name"` to use the declared alias exclusively
(definitions with an absent or `null` alias still use their key; an explicit
empty-string alias remains a valid source key). Use `match="key"` to
disable aliases entirely; the default `match="both"` keeps the precedence above.
`save_meta` writes four-space indentation like v1 `Meta.writefile`;
pass `indent=` to choose another.

The second argument may also be a definition Mapping. Filter a shared definition
in memory and pass it directly to `build_meta`; no temporary JSON file is needed.
String values are stripped before checking emptiness. For both `""` and
whitespace-only inputs, `build_meta` applies the following policy:

| Schema type | Default | `keep_empty_strings=True` |
|---|---|---|
| `string` | Omit the value | Keep `""` if the format permits |
| `number`, `integer`, `boolean` | Omit before conversion | Raise `StructuredError` (`ecode=1`) |

The same policy applies to repeated cells without removing their row positions.
Nonempty invalid typed values still raise conversion errors in either setting.
This normalization is specific to `build_meta`: v1 `Meta.assign_vals` and
`parse_invoice_meta` retain their existing rules, including conversion errors
for whitespace-only number, integer and boolean values.

To update `invoice.custom` as v1 `castval` / `_assign_invoice_val` did, use
`set_custom_fields(invoice, updates, schema=...)` (#603). It returns a new
`InvoiceData`; each value is cast by the field's `type` and `format` in
`invoice.schema.json`:

| Schema | Accepted values | Stored value |
|---|---|---|
| `integer` | digits with an optional unit (`"12 mm"`), an integral float (`3.0`) | `int` |
| `number` | numeric text with an optional unit | `int` when integral, else `float` |
| `boolean` | `"true"` / `"false"` (any case), other values by truthiness | `bool` |
| `string` + `date` / `date-time` / `time` | text dateutil can parse, `date` / `datetime` objects | `2023-07-19` / ISO 8601 / `13:04:05` |
| `string`, other or no format | anything | unchanged |
| any type | `None`, NaN, `NaT`, `pd.NA` (NumPy NaN / NaT included) | `None` |

Blank cells read with `dtype_backend="numpy_nullable"` (`pd.NA`) are also stored as `None`. NumPy
scalars (such as `np.int64`) are cast as the equal Python value, so the result saves with `save_invoice`.

An undeclared key or a value that does not fit raises `StructuredError` (code 1);
a type mismatch uses v1's message. Pass
`schema=paths.tasksupport / "invoice.schema.json"`: the injected invoice carries
its schema only for ExcelInvoice and SmartTable row tiles. Write the result with
`save_invoice(invoice, out)`. To fill values from spreadsheet columns,
`resolve_custom_key(schema, label)` returns the key whose `label.ja` or
`label.en` equals the label (`lang="ja"` or `"en"` restricts the language). An
unknown label, or a label shared by two fields, raises `StructuredError`.

<!-- test: ga603-custom-fields -->
```python
from rdetoolkit.nodes import resolve_custom_key, set_custom_fields
from rdetoolkit.types import InvoiceData

schema = {"properties": {"custom": {"properties": {
    "measured_date": {"type": "string", "format": "date", "label": {"ja": "測定日", "en": "Measured date"}},
    "cycles": {"type": "integer", "label": {"ja": "サイクル数", "en": "Cycles"}},
}}}}
invoice = InvoiceData(raw={"custom": {"measured_date": None, "cycles": None}}, schema=schema)
row = {"測定日": "2023/07/19", "Cycles": "12"}
updates = {resolve_custom_key(schema, label): value for label, value in row.items()}
invoice = set_custom_fields(invoice, updates)
assert invoice.raw["custom"] == {"measured_date": "2023-07-19", "cycles": 12}
```

For file and image artifacts, `read_excel` accepts worksheet, header, row and
column selections; `save_csv` accepts precision, header and index options.
`save_csv(..., preamble=...)` writes a block of lines before the table, such as
the `#title` / `#legend` header `rdetoolkit.graph` reads: rows (which may differ
in length) are written in the table's CSV format, a str is written verbatim, and
`blank_line_after_preamble=True` adds one empty line before the table.
`save_json` and `save_text` accept an output `kind`. Use `read_json` for detected
encoding, `save_invoice` for the tile invoice formatting contract, and
`save_figure` for caller-owned matplotlib figures. `plot_lines` accepts x/y
columns or independent pairs, labels, title, scale, legend, size, DPI and kind.
Pairs may be `(x, y, label)`, or `labels=` names every series; `grid=True` draws
the grid, and axis-label sizes follow matplotlib rcParams unless
`label_fontsize` is set. Axis ranges, as in v1 `csv2graph(..., xlim=..., ylim=...)`
or `ax.set_xlim` / `ax.set_ylim`, are `xlim` / `ylim`, and `xscale` sets the x
axis scale; a `None` bound stays automatic, so `ylim=(0, None)` starts the axis
at 0. Series with their own x values and length, such as the regions of a
multi-region measurement, can be passed as a list of data frames: the x/y or
pair selection applies to each frame, and `labels=` names the series in frame
order (no `pd.concat(axis=1)` into one frame is needed).
Both plot nodes save with a tight bounding box by
default: pass `bbox_inches=None` to reproduce a plain v1 `fig.savefig(path)`, or
`pad_inches=0` for `savefig(path, bbox_inches="tight", pad_inches=0)`.
Templates that select rows by cell colour use
`read_excel_fills(path, column="A", ...)` with the same sheet and row options as
`read_excel`; it returns one fill colour (ARGB hex, `theme:<n>` or `None`) per
data-frame row. `OutputContext` has no run-scoped temp directory (v1
`resource_paths.temp`); use `tempfile.TemporaryDirectory()` for scratch files,
which are removed when the block ends.

`unzip_inputs` returns absolute paths to extracted files in archive order.
Directory entries and unsafe destinations are excluded; repeated archive members
produce repeated paths. Existing containment checks, including outward symlinks,
still apply. Callers that ignored the old return value can keep doing so.
Pass `include_dirs=True` to also receive directory entries, including empty
directories, when listing the archive structure.

### Load settings and override the mode in main.py

To prepare configuration before entering a flow, use
`rdetoolkit.runner.load_run_config(root=None, *, overrides=None)`.
`root` accepts a project or data directory as a `Path` or string and defaults to
the current directory. The helper uses the Runner's data-root resolver and
discovery order: project-root `rdeconfig.yaml`, project-root `pyproject.toml`,
then `tasksupport/{rdeconfig.yaml,rdeconfig.yml,pyproject.toml}` under the resolved
data root. Tasksupport files are interpreted as v1 configuration (Design §6.3).

`overrides` merges recursively over the discovered settings. Pass the returned
`RdeConfig` to `run(flow=..., config=...)` to use the entire object as the
configuration. Passing a mapping directly also overrides discovered settings.
This example changes the mode while retaining other tasksupport values.

<!-- test: load-run-config -->
```python
from rdetoolkit import flow, workflows
from rdetoolkit.runner import load_run_config
from rdetoolkit.types import RdeConfig


@flow
def pipeline(config: RdeConfig) -> None:
    print(config.system.extended_mode)


config = load_run_config(overrides={"system": {"extended_mode": "MultiDataTile"}})
report = workflows.run(flow=pipeline, config=config)
if report.status != "success":
    raise SystemExit(1)
```

`RdeConfig.model_validate({"system": {"extended_mode": None}})` is also accepted.
YAML `null` and a `None` override normalize to an unset mode with the default
value `"invoice"`. SmartTable / ExcelInvoice detection then emits no W1001.
A conflicting mode explicitly set as a string still emits W1001 (Design §6.2).

## Runtime changes

In a production `main.py`, opt into nonzero exits for failed or partial runs.
The run report, `job.failed` on failure, and completed artifacts are finalized
before exit. A success returns normally; failed exits with 1 and partial with 2.
The default library call still returns a `RunReport` for inspection. Its public
`exit_code` property uses the same mapping as the CLI and can also be passed to
`SystemExit`; it is derived and adds no JSON field or schema version.

<!-- test: ga572-main -->
```python
from rdetoolkit import workflows
from processing import pipeline

workflows.run(flow=pipeline, exit_on_failure=True)
```

Template discovery imports skeleton providers declared in root Python modules
and the conventional `modules/` package when `--module` is omitted; installed
plugins remain discoverable. Use `--module` to select other provider modules.
Template descriptions include slot documentation and domain annotations while
omitting standard library types. Processing-template init generates `main.py`,
the implementation and a test skeleton; all three have overwrite protection.
Slot signatures must still match exactly, including parameter names and kinds.
Add optional hooks when evolving a published skeleton; adding a required slot
requires updating its concrete implementations. The depth-2 and flow-boundary DI
rules remain unchanged (Design §5.2).

`migrate apply` preserves unsupported cross-module entries and helper files,
and reports the callback requiring manual migration. Convert that callback and
its entry together. Supported local callbacks preserve comments and literals;
removal of the legacy entry is explicitly reported with the flow CLI invocation.

- A v1 `main.py` that rewrites `data/inputdata/` before calling `run()`
  (splitting a concatenated instrument file, building a SmartTable CSV and its
  zip) declares that step with the flow decorator's `prepare=prepare_inputs`
  option, with
  `def prepare_inputs(inputdata: Path, config: RdeConfig) -> None`. The Runner
  calls it once per run, after loading the configuration and before resolving
  the mode, so both `workflows.run(flow=...)` and `rdetoolkit run <pkg.mod:flow>`
  see the prepared inputs. Without it, `rdetoolkit run` resolves the mode from the
  unprepared files. `--validate-only` also runs it, so the pre-flight checks
  the same mode as the real run but may modify `inputdata/`; write it to be
  idempotent (a re-run and `rdetoolkit repro` see the already-prepared
  inputs). It receives a copy of the configuration. It is recorded as
  `prepare.started` / `prepare.completed` / `prepare.failed` events. The
  flow's `error_code` / `error_message` options apply to its failures as to
  the body's; without them an ordinary exception fails the run with 3001
  before any tile. A `StructuredError` keeps its own code and message. Only
  the flow the Runner executes is prepared (a nested flow's `prepare` is not
  run), and direct calls of the flow do not run it.
- Use the flow decorator with `error_code=7, error_message="Cannot process input"` to map body (and prepare)
  failures to one code and message through either v2 entry. Supplying only a
  code preserves the original message; supplying only a message uses 3001.
  The message may contain `{error}` (the exception's text) and `{error_type}`
  (its class name), e.g. `error_message="Cannot read sample: {error}"`; other
  braces are kept as written.
  A `StructuredError` raised in the body keeps its own code and message, as
  with v1 `catch_exception_with_message`.
  Direct function calls still propagate the original exception. The original
  exception remains chained in Runner failures; process-control exceptions
  such as `KeyboardInterrupt` and `SystemExit` are not mapped.
- **When rewriting v1 `catch_exception_with_message` as a flow, set `error_code=1` explicitly.**
  The v1 decorator turns a plain exception into a `StructuredError` with
  `ecode=1` and an `Error: ` prefixed message. Moving only `error_message` to
  the flow decorator uses 3001, so the `job.failed` `ErrorCode` changes from 1.
  The mapping that reproduces the v1 result is:

  | v1 `catch_exception_with_message` arguments | flow decorator arguments |
  |---|---|
  | `error_message="m"` | `error_code=1, error_message="Error: m"` |
  | none | `error_code=1, error_message="Error: {error}"` |
  | `error_code=c, error_message="m"` | `error_code=c, error_message="Error: m"` |

  If you do not need the `Error: ` prefix, `error_code=1, error_message="m"`
  and, without arguments, `error_code=1` alone keep the same code (the
  message is then `m` or the exception's text respectively).
- `InputPaths` injected into a flow uses paths relative to the working directory,
  like v1 input paths. Path-based user error messages therefore keep the v1
  spelling. The Runner still resolves the data root once for its internal work.
- The canonical v2 return value is `RunReport`. Start from `report.status` and
  `report.iterations`.
- **On the flow entry point, `on_iteration_error` defaults to `continue`.** If you
  need v1's immediate stop (fail-fast), set `fail_fast` explicitly. The v1 entry
  point `run(custom_dataset_function=...)` keeps v1's iteration rules (see
  "Intentional differences" below).
- The graph is a call sequence recorded after execution, not a pre-execution DAG.
  Ordinary Python control flow works as is.
- MultiDataTile assigns its tiles (`data/`, `divided/0001`, ...) in file name order,
  as v1's MultiDataTile did. A v1 structured program that listed `inputdata` itself,
  such as `for f in inputdata.glob("*")`, got directory order instead. To keep that
  order, set `multidata_tile.order: filesystem` (the default is `name`). The listing
  order depends on the filesystem (#597).

## CLI command renames

v2.0 reorganizes the CLI into `rdetoolkit <noun> <verb>` commands. Commands from v1
keep working in v2.0.x as deprecated aliases that print a warning and are removed
in v2.1; names that existed only in v2 release candidates were removed without an
alias. Update scripts, CI definitions and Dockerfiles to the new names.

| Old | New | Origin |
|---|---|---|
| `gen-config [OUTPUT_DIR] [--template X] [--overwrite]` | `new config [-o DIR] [--preset X] [--force]` | v1 — deprecated alias kept in v2.0.x, prints a warning, removed in v2.1 |
| `gen-invoice` | `new invoice` | v1 — deprecated alias |
| `make-excelinvoice` | `new excelinvoice` | v1 — deprecated alias |
| `csv2graph` | `plot` | v1 — deprecated alias |
| `artifact --output-archive` | `package -o/--output` | v1 — deprecated alias |
| `run TARGET` (`module::attr`) | `run --legacy TARGET` | v1 — the `::` form without `--legacy` still runs (no warning, for output compatibility); `--legacy` becomes required in v2.1 |
| `init --processing-template X` | `new processing X` | v2 rc only — removed, no alias |
| `run --flow X` | `run X` | v2 rc only — removed |
| `graph REPORT` | `report trace REPORT` | v2 rc only — removed |
| `templates list/describe` | `skeletons list/show` | v2 rc only — removed |
| `nodes describe`, `flows describe` | `nodes show`, `flows show` | v2 rc only — removed |
| `migrate apply --out DIR` | `migrate apply -o/--output DIR` | v2 rc only — removed |

`rdetoolkit migrate check` reports the old command names it finds in Python string
literals and in `*.sh`, `*.yml`, `*.yaml`, `*.toml`, `*.cfg`, `Makefile` and
`Dockerfile` files. See the [command line page](usage/cli.en.md) for every command.

## Compatibility scope and schedule for v1 users

This section is final as of 2.0.0rc1. The v1 execution path (the iteration loop
and the per-mode processing) has been removed and every entry point runs through
a single Runner. The v1 **contract** (entry point, artifacts, how a run ends) is
protected by tests that compare against contract snapshots frozen from the v1 execution path carrying the v1.7.1 contract.

### What is kept

- **Entry point**: the signature of
  `rdetoolkit.workflows.run(custom_dataset_function=...)`. The callback still
  receives `(srcpaths, resource_paths)`.
- **The v1 contract**: the returned JSON (the per-tile status list),
  `SystemExit(1)` on failure, fail-fast by default, the `data/job.failed` format,
  the output directory layout (`raw/`, `structured/`, `divided/NNNN/` and so on),
  and `data/logs/rdesys_<timestamp>.log`.
- **Tier 1 API**: `rdetoolkit.models.rde2types`, `rdetoolkit.rde2util`,
  `rdetoolkit.invoicefile`, `rdetoolkit.errors`, `rdetoolkit.exceptions`,
  `workflows.check_files` / `check_files_result`, and
  `workflows.generate_folder_paths_iterator`.
- The v1 CLI commands: `rdetoolkit init` and `rdetoolkit validate` keep their names,
  and the renamed v1 commands keep working in v2.0.x as deprecated aliases (see
  [CLI command renames](#cli-command-renames)).

### What was removed (2.0.0rc1)

- The `rdetoolkit.modeproc` module.
- The `rdetoolkit.processing` package (`Pipeline`, `ProcessingContext`,
  `Processor` and all of its subclasses).
- The per-mode functions in `rdetoolkit.workflows`: `invoice_mode_process`,
  `excel_invoice_mode_process`, `multifile_mode_process`,
  `rdeformat_mode_process` and `smarttable_invoice_mode_process`.
- The public `impl` and `interfaces` exports of the `rdetoolkit` package. Both
  modules remain as internals of the Runner but are not public API.

Code that imports any of these directly should go back to calling
`run(custom_dataset_function=...)` or move to a flow function.

**Deprecated (no caller left, kept only for compatibility)**:
`rdetoolkit.errors.handle_and_exit_on_structured_error` and
`rdetoolkit.models.result.WorkflowResultManager`. Do not use them in new code.
The `smarttable_rowfile=` argument of `RdeOutputResourcePath` also remains, as in
v1.7, a deprecated alias of `smarttable_rawfile`.

### Behaviour changes

**Introduced in the v1.7 line (unchanged in v2)**

- In SmartTable mode the row CSV (`fsmarttable_*.csv`) is not part of `rawfiles`
  (#503). Use `smarttable_rawfile` when you need the row CSV (the old name
  `smarttable_rowfile` was a misspelling and has been renamed).
- With `smarttable.save_table_file: true` the original SmartTable file is
  registered first, as `divided/0001`, and the data rows move to `divided/0002`
  onwards (#503).
- A SmartTable `meta/<key>` column requires `tasksupport/metadata-def.json`.
  Without it the run fails with `StructuredError` instead of silently ignoring
  the column (#496).

**Introduced in 2.0.0rc1**

- Every run writes an event log, `data/logs/events_<run_id>.jsonl`, by default.
  The file is capped at 64 MiB per run: when the cap is reached, warning **W1002**
  (`EventsLogTruncated`) is recorded once and only the node-level events after
  that point are dropped (run-level and tile-level events and warnings are
  kept). `data/logs/**` is not part of the v1 artifact contract.
- `data/logs/iterations/` is emptied when tile iteration starts. `job.failed`,
  `run_report_*` and `events_*` are kept across runs, as before.

**Introduced in 2.0.1: `templates/` is renamed to `template/`**

- `rdetoolkit init` generates `template/tasksupport/` instead of
  `templates/tasksupport/`, so all generated directories (`container/`,
  `input/`, `template/`) have singular names.
- A project created by v1 still has `templates/tasksupport/`. Run
  `rdetoolkit migrate apply <project>` on the project root. The dry run lists
  the `templates/` → `template/` move next to the Python conversions. With
  `--no-dry-run`, the output directory (`--out`, or `<name>_migrated`) contains
  `template/`; the input directory is not changed. `migrate check <project>`
  reports `templates/` as a finding.
- If the project has both `templates/` and `template/`, `migrate apply` stops
  with exit code 3 and does not merge them. Move the files you want to keep
  into `template/`, remove `templates/`, and run it again.
- Until you migrate, `validate all` reads `templates/tasksupport/` when
  `template/tasksupport/` does not exist and reports a `deprecated_layout`
  warning. The warning does not change the exit code, but `--strict` fails on it.
- `init` run in a directory that has `templates/tasksupport/` does not create
  `template/`. It prints a warning that points to `migrate apply`.
- `migrate apply` renames only the directory. Update paths you wrote yourself,
  such as `[tool.rdetoolkit.init]` entries in `pyproject.toml` or CI scripts
  that copy schemas into `templates/tasksupport/`.

### Intentional differences (cases where v2's result differs from v1)

A header-only Excel invoice is rejected before tile execution. The compatibility
callback entry preserves v1's generic failure (999); the flow entry reports
the input validation error `EmptyExcelInvoice` (4004), with guidance to add data
rows. A workbook missing its invoice sheet keeps its existing error contract.

| Case | v1 | v2 |
|---|---|---|
| The callback raises `StructuredError(msg, ecode)` | `ecode` and `msg` in `job.failed` | Same |
| The callback raises a plain exception | `ErrorCode=999`, `Unexpected error in <mode> mode: ...` | `ErrorCode=3001`. The message is the error-catalogue E3001 text and contains your exception's message |
| stderr traceback when the callback fails (`traceback:` settings / `TRACE_*`) | Formatted by `errors.handle_exception` as `compact` / `python` / `duplex` from `Config.traceback`, else `TRACE_*`, else the python form | Same formatter, same settings and the same choice order on the v1 callback entry; the settings raise no warning. For a plain exception the outermost exception shown is `TileExecutionError` with the E3001 message (chained from your exception) instead of `StructuredError: Unexpected error in <mode> mode: ...`. When `run()` is itself called from inside an `except` block, the exception chain is shown as Python recorded it (1.7.1 dropped the callback's own implicit context in that case). Failures outside the callback (configuration, invoice validation, output validation and so on) also print the traceback of the error `job.failed` reports, in the same format. The flow entry (`run(flow=...)`, `rdetoolkit run <module>:<flow>`) writes no such traceback, and a v2 `rdeconfig.yaml` at the project root rejects `traceback:` (E1002) |
| `invoice.schema.json` itself is invalid and the callback also fails | The callback's error code (v1 validated after the callback) | `ErrorCode=4001` with the schema-validation reason. The callback is not called |
| The invoice violates its schema | A mode-specific code; in some modes the callback had already run and outputs were created | `ErrorCode=4001`. The callback is not called and no tile artifacts are created (`job.failed`, the logs and the run report remain) |
| Configuration discovery (`config=None`) | Loaded from `data/tasksupport` | Same. An invalid configuration file is `ErrorCode=999`, as in v1 |

The `Meta.assign_vals` row is a bug fix in the Tier 1 API, so it also applies on the
v1 callback entry. The 1.7 line has the same bug, but no 1.7.x release with the fix
has been published yet. The v1 column shows the behaviour of 1.7.1, the latest v1
release, and rolling back to 1.7.1 restores it. If a later 1.7.x release carries the
same fix, this row no longer differs from that release.

For the run-level invoice row, rely on the seeded tile invoice for registration
values and compute any tile-specific value inside that tile's flow, then write it
with `save_invoice`.

### Rollback

If v2 causes problems, pin `1.7.1`, the latest v1 release (for example
`rdetoolkit==1.7.1` in `requirements.txt`). The development build that still
contains the old execution path is not on PyPI; it can only be installed from
source at the git tag `v2.0.0a1` (for diagnosis only; that tag reports
`__version__` as `2.0.0`).

### Schedule

Releases go `2.0.0rc1` → GA `2.0.1`. The version number `2.0.0` is skipped and
will not be published as a final release.
