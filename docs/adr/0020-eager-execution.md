# ADR-020: Trace 方式を廃止し、eager 実行に転換する

- 状態: 採用
- 日付: 2026-06

## 状況

v2 の初期設計では、フロー関数を代理実行(トレース)して静的な DAG を組み立て、検証してから
実行する方式を採っていました。検証の結果、この方式には次の問題があることが分かりました。

- 構造化処理を書く研究者が自然に書くコード — `if result == 3:` のような分岐、f-string、
  リテラル引数、`for` ループ、コンテナの受け渡し — が、エラーにならずに誤った DAG に
  変換される。個々のパターンを禁止しても網羅はできない。
- 設定値による分岐やリテラル引数という、構造化処理に必須の書き方と両立しない。
- 想定する規模(1 フローあたり数個〜数十個のノード、ほぼ直線的な処理)では、実行前の静的検証の
  利点が実装と学習のコストに見合わない。

「Python をトレースしてグラフを作る」方式から eager 実行へ移る流れは、他の Python
フレームワークでも繰り返し見られます。

## 決定

DAG の事前構築(トレース・コンパイル)を廃止し、フローを普通の Python 関数としてそのまま
実行する。ノードの呼び出しは実行時に記録し、実行の説明は記録から事後に作る。

> グラフは「書く」ものではなく「観測される」ものである。

## 帰結

- 分岐・ループ・リテラル・f-string・デフォルト引数・コンテナは、すべて Python の意味どおりに動く。
- フローとノードは、直接呼び出して pytest でテストできる。
- 実行前の完全な配線検証(ExecutionPlan)は失われる。代わりに、登録の静的検査
  (`nodes lint`)、ドメイン検証のみの実行(`run --validate-only`)、テンプレートの import 時検証、
  前回の実行記録(`graph`)を提供する。
- 性能が必要になった場合の拡張点は、データタイル単位の並列化とする。ノード単位の並列化は
  実行前の DAG 解析を必要とし、この決定と矛盾するため採用しない。
- 将来 GUI でフローを組み立てる機能を加える場合は、ノードレジストリの型情報をもとに、
  人が明示的に結線する宣言的なグラフ表現として別の層に追加する。
