# ADR-023: 単一 Runner への統合と契約レベルの v1 互換

- 状態: 採用
- 日付: 2026-07-15
- 吸収: [ADR-021](0021-conditional-v1-sunset.md)

## 状況

v1 と v2 の実装を並べて保守すると、不具合の修正や依存関係の更新を 2 回行う必要があり、
入口によって設定・戻り値・エラー方針・実行記録の扱いが異なる状態が続きます。

一方、利用者が依存しているのは v1 の実装そのものではなく、次の公開面です。

- 入口 `run(custom_dataset_function=...)` とコールバックの引数型
- 成果物の契約: ディレクトリ構成、invoice・raw・サムネイル、`job.failed` の形式、終了コード、
  `StructuredError` から `job.failed` への変換
- 直接 import されている公開 API: `rde2types`、`rde2util`、`invoicefile`、`errors`、`exceptions`

## 決定

1. **単一 Runner**: フローの入口と v1 コールバックの入口を同じ実行要求に正規化し、同じ Runner・
   エラー方針・イベント・RunReport・終了処理で実行する。v1 の実行経路は v2.0 の正式リリースまでに削除する。
2. **互換性の単位を「コード」から「契約」に変える**: 上記の公開面を維持し、v1 の実行結果から
   作って凍結したテスト用の期待値(契約 fixture)で保証する。v1 実装とのバイト単位の一致は保証しない。
3. **設定の一本化**: Runner の内部では v2 の設定モデルだけを使う。v1 の設定は入口で変換する。
   v1 の成果物に関する設定項目は、v1 と同じ既定値で v2 の設定にも追加する。
4. **コールバックの記録**: v1 のコールバックはフローとして記録する。コールバック内で呼ばれた
   ノードは同じ実行記録に残り、`graph`・`report`・`repro` を v1 の入口でも使える。

## 帰結

- 保守する実行経路が 1 つになり、エラー方針・イベント・レポートがすべての入口で一貫する。
- v1 の利用者はコードを変更せずに動作を続けられる。v1 の入口に非推奨警告は出さない。
- v1 との差は凍結した契約 fixture の範囲で検出するため、互換性の品質は fixture の網羅度に依存する。
  5 つのモードの正常・異常の代表ケースと、実運用に近いプログラムで補う。
- v1 の入口では、データタイルの失敗時の既定の振る舞いは v1 と同じ `fail_fast` のまま、フローの
  入口では `continue` とする。v1 と結果が意図的に異なる点は [v1 から v2 への移行](../migration_v1_to_v2.md)
  に一覧している。
